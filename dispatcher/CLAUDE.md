# CLAUDE.md (dispatcher/)

This file provides guidance to Claude Code when working with the `dispatcher/` package (and its companion firmware in `pico/`). See the repo root `CLAUDE.md` for the rest of the architecture.

### RFID dispatcher (`dispatcher/`) and Pico firmware (`pico/`)

The dispatcher adds autonomous, block-protected train movement on top of the manual BLE control path documented in the root CLAUDE.md — RFID tags at track block boundaries let the system know where each train is, instead of relying purely on manual `/train` calls.

- Each train carries a **Raspberry Pi Pico 2 W + MFRC522 RFID reader**, running the MicroPython firmware in `pico/` (`main.py`, vendored `mfrc522.py`, per-train `config.py` copied from `config.example.py`). Like `hubs/`, this is firmware for separate hardware/runtime — not part of the pytest-covered package (`pytest.ini` omits both `hubs/*` and `pico/*` from coverage). See `pico/README.md` for wiring/flashing.
- The Pico publishes tag reads over MQTT (`train/{train_id}/tag`) to a Mosquitto broker on the central Pi; `dispatcher/mqtt_bridge.py::MqttBridge` subscribes to `train/+/tag` and hands events from paho-mqtt's network thread to the dispatcher's asyncio loop via `call_soon_threadsafe`.
- `dispatcher/track_model.py::TrackModel` models the *real* physical track (10 switches: 7 motorized/3 manual as graph nodes -- ids A-I plus K, no J -- 15 directed `Edge`s between switch ports as segments, 14 `Sensor`s sitting on edges for position detection, 15 `Block`s for occupancy) — it's the actual layout, not a sample, sourced from the track designer's topology export; `TrackModel()` builds it directly. A and C are physically getting motors too but aren't wired yet, so they're still MANUAL for now -- update `_build_switches` (and `SWITCH_WIRING`) once they are. B has a motor wired (hub 5) but was reverted to MANUAL on 2026-08-17 because hub 5's BLE connection is unreliable (stale status notifications, commands failing verification) -- flip it back to MOTORIZED once hub 5 is fixed. BLE wiring (switch hub_id/port_name) and physical RFID UIDs aren't hardcoded into the topology — they're populated at runtime via `configure_switch_wiring()`/`configure_sensor_uid()`, driven by `Settings.switch_wiring`/`Settings.sensor_uid_mapping` (empty by default; `dispatcher/factory.py::build_dispatcher` applies them). `TrackModel.sensor_id_for_uid()` maps a physical scanned UID to a logical sensor id (falls back to treating the sensor id itself as the UID when unconfigured, e.g. in tests/mock mode).
- Trains are registered via `TrackModel.register_train(train_id, hub_id, route=..., smart_drive=...)`, where `route` is a train's fixed, pre-assigned cyclic list of switch ids (from `Settings.train_hub_mapping` + `Settings.train_routes`) — used unless `smart_drive=True` (`Settings.train_smart_drive`), in which case `route` is omitted and the train instead calls `TrackModel._choose_next_edge()` at each decision point: a greedy heuristic that always picks the least-recently-visited edge leaving its current switch (a never-visited edge always outranks a visited one; there's no "visited set that resets once locally exhausted," since that traps a train shuttling forever between two switches whenever it exhausts what's visible from there, without ever taking the one edge that would lead further away), avoids immediately reversing back the way it came unless that's the only option, prefers an exit whose block no other train holds (two trains each insisting on the other's least-recently-visited edge deadlock head-on; if every exit is held it still picks the oldest and queues), and — since 3 switches (A, B, C) are `MANUAL` with no position field or way for software to read/set their physical state — never chooses to depart a switch via a MANUAL switch's STRAIGHT/DIVERGE port (only its always-connected TRUNK port is a safe pass-through). `TrackModel.hops_to_switch()` (the contention tiebreak distance) falls back to `find_route()`'s BFS edge count for smart-drive trains instead of a route-index offset, since they have no fixed list to index into — `BlockManager.resolve_contention` itself is unaware of the difference. Only 11 of the 15 blocks carry a sensor (AK, FI, GH, IK -- short hops between adjacent switches -- have none), so a single tag read can't confirm every block on its own: `TrackModel.next_block_chain_for_train()` returns the next *chain* of edges to grant — spanning consecutive sensorless edges and stopping at (inclusive of) the first sensored one — and `record_tag_event()` confirms/clears the whole chain together once that sensor fires. Chains are granted and released as a unit, all-or-nothing, the same way switch-setting already is.
- `dispatcher/block_manager.py::BlockManager` grants/queues block entry per *chain* and sets required switches (all-or-nothing, skipping manual switches which it only logs) via the *same* `SwitchController.send_command_with_retry` used by the REST API. Contention between two trains wanting the same block is resolved by route-hop distance (farther train holds; ties break lexically by train_id — see `resolve_contention`'s docstring for the full rationale).
- `dispatcher/dispatcher.py::Dispatcher` is the orchestrator: on each tag event it updates position, releases blocks (see below: the *previous* chain, not the one just confirmed), and either advances the train (stop/resume via the *same* `TrainController.handle_command` used by the REST API) or holds it. A watchdog stops every train if one misses an expected tag within `dispatcher_watchdog_timeout`, auto-clearing once that train next confirms a *pending* tag. Watchdog timing uses the dispatcher's own receive time, never `TagEvent.timestamp`: a Pico's clock is unsynced (years off) until NTP succeeds, which otherwise trips the watchdog instantly. A moving self-drive train holding a granted chain that reads a sensor not on it is treated as position lost and stops every train (a read on the last-confirmed edge is benign -- edge BK carries tags 2, 14 and 5, and the reader repeats tags), and stray reads do not refresh the watchdog. The one exception is a single missed read on a fixed route: if the unexpected sensor is the next one on the train's route (`TrackModel.lookahead_chain_for_sensor`) and `BlockManager.try_claim` finds every skipped block free, the earlier read is treated as missed (logged as a warning) and both chains are confirmed together; smart-drive trains get no such tolerance. Because a switch is otherwise only set once a tag confirms the previous chain, a missed read would leave the next switch wrong (a switch hub keeps its default position after a power-cycle), so `Dispatcher._preset_next_chain_switches` sets the *following* chain's switches as soon as a chain is granted, best effort, skipping any switch a granted chain or another train's current position depends on (`TrackModel.switches_reserved_from`).
- **Blocks are released a chain late, because the reader is on the nose.** Each train's reader is at the front and the trains are ~26 cm long, so a confirmed tag read means the nose is at the tag with the tail still behind it, usually in that chain's last block. `Dispatcher._edges_safe_to_release` therefore frees the *previously* confirmed chain and holds the one just confirmed until the next read (an edge reused by the new chain stays held). Freeing at the read let a waiting train drive into a block the tail was still in (`dispatcher/simulate.py` collided in 100% of two-train runs before this). Consequently a held train occupies two chains, and tags need to sit far enough into a block (>= train length, ~30 cm) that reading one means the tail has left the previous block.
- **Start positions are held, not free.** `Dispatcher._claim_start_blocks` (called from `set_self_drive(enabled=True)`) claims every free block touching the train's recorded switch, since before its first tag read nothing else says where it physically is; they are freed at its first confirmed read, and a warning is logged if another train already holds one (overlapping start positions). `register_train`'s `start_switch` still has no config setting: `factory.py` doesn't pass it, so every smart-drive train is registered at the first switch (D) until that's wired up.
- `POST /dispatcher/reset` (`Dispatcher.reset()`) stops every train and returns the dispatcher to its just-started state -- start positions, no held blocks/pending chains, emergency latch cleared, self-drive off -- without touching any BLE connection. Use it after repositioning trains by hand instead of restarting the service, since a restart drops every hub and switch hubs then need a physical power cycle. Place each train at its route's first switch before re-enabling self-drive.
- **Actuation is in-process, not via MQTT** — the dispatcher calls `TrainController`/`SwitchController` directly (it's constructed via `dispatcher/factory.py::build_dispatcher` sharing `controller.train_controller`/`controller.switch_controller` from `webservice/train_service.py`'s `LegoController` singleton). `MqttBridge.publish_command()` exists for future direct Pico-side motor control but isn't called yet, since the Pico firmware currently only logs command messages.
- Manual REST commands (`/train`) **bypass the dispatcher entirely** in this version — no reconciliation between manual control and dispatcher-driven movement. `Train.hub_id` (and everywhere `TrainController.handle_command` is called) is a BLE address string, not an integer -- trains are controlled over GATT, unlike switches.
- `dispatcher/simulate.py` runs the *real* `Dispatcher`/`BlockManager`/`TrackModel` against simulated smart-drive trains in virtual time (`python -m dispatcher.simulate --trains 2 --duration 1800 --seeds 20`, exits non-zero on any violation) and reports collisions, trains moving without a granted chain, deadlocks, e-stops, stopped-time and path repetitiveness. Its physical model is an assumption set (random 3-6 s edge traversal times, 26 cm trains at an assumed 25 cm/s, sensor at `--tag-fraction` along the edge, MQTT/BLE latency, instant switches, no watchdog), so treat results as "safe/unsafe under these assumptions", not proof about the layout. Current state: 2 trains run clean (300 seeds x 1800 s); 3 trains still deadlock most of the time, so don't run more than 2 smart-drive trains. It reaches into `Dispatcher._handle_tag_event` and `BlockManager._pending/_reserved_by` directly.
- Wired into `webservice/train_service.py`'s existing `startup_event`/`shutdown_event` via `asyncio.create_task(dispatcher.run())` / `await dispatcher.stop()`, gated by `settings.dispatcher_enabled` (tests force this off via `DISPATCHER_ENABLED=false` in `tests/conftest.py`, since there's no broker in CI).
