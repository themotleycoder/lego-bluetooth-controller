# CLAUDE.md (dispatcher/)

This file provides guidance to Claude Code when working with the `dispatcher/` package (and its companion firmware in `pico/`). See the repo root `CLAUDE.md` for the rest of the architecture.

### RFID dispatcher (`dispatcher/`) and Pico firmware (`pico/`)

The dispatcher adds autonomous, block-protected train movement on top of the manual BLE control path documented in the root CLAUDE.md — RFID tags at track block boundaries let the system know where each train is, instead of relying purely on manual `/train` calls.

- Each train carries a **Raspberry Pi Pico 2 W + MFRC522 RFID reader**, running the MicroPython firmware in `pico/` (`main.py`, vendored `mfrc522.py`, per-train `config.py` copied from `config.example.py`). Like `hubs/`, this is firmware for separate hardware/runtime — not part of the pytest-covered package (`pytest.ini` omits both `hubs/*` and `pico/*` from coverage). See `pico/README.md` for wiring/flashing.
- The Pico publishes tag reads over MQTT (`train/{train_id}/tag`) to a Mosquitto broker on the central Pi; `dispatcher/mqtt_bridge.py::MqttBridge` subscribes to `train/+/tag` and hands events from paho-mqtt's network thread to the dispatcher's asyncio loop via `call_soon_threadsafe`.
- `dispatcher/track_model.py::TrackModel` models the *real* physical track (10 switches: 7 motorized/3 manual as graph nodes -- ids A-I plus K, no J -- 15 directed `Edge`s between switch ports as segments, 9 `Sensor`s sitting on edges for position detection, 15 `Block`s for occupancy) — it's the actual layout, not a sample, sourced from the track designer's topology export; `TrackModel()` builds it directly. A and C are physically getting motors too but aren't wired yet, so they're still MANUAL for now -- update `_build_switches` (and `SWITCH_WIRING`) once they are. B has a motor wired (hub 5) but was reverted to MANUAL on 2026-08-17 because hub 5's BLE connection is unreliable (stale status notifications, commands failing verification) -- flip it back to MOTORIZED once hub 5 is fixed. BLE wiring (switch hub_id/port_name) and physical RFID UIDs aren't hardcoded into the topology — they're populated at runtime via `configure_switch_wiring()`/`configure_sensor_uid()`, driven by `Settings.switch_wiring`/`Settings.sensor_uid_mapping` (empty by default; `dispatcher/factory.py::build_dispatcher` applies them). `TrackModel.sensor_id_for_uid()` maps a physical scanned UID to a logical sensor id (falls back to treating the sensor id itself as the UID when unconfigured, e.g. in tests/mock mode).
- Trains are registered via `TrackModel.register_train(train_id, hub_id, route)`, where `route` is a train's fixed, pre-assigned cyclic list of switch ids (from `Settings.train_hub_mapping` + `Settings.train_routes`). Only 8 of the 15 blocks carry a sensor, so a single tag read can't confirm every block on its own: `TrackModel.next_block_chain_for_train()` returns the next *chain* of edges to grant — spanning consecutive sensorless edges and stopping at (inclusive of) the first sensored one — and `record_tag_event()` confirms/clears the whole chain together once that sensor fires. Chains are granted and released as a unit, all-or-nothing, the same way switch-setting already is.
- `dispatcher/block_manager.py::BlockManager` grants/queues block entry per *chain* and sets required switches (all-or-nothing, skipping manual switches which it only logs) via the *same* `SwitchController.send_command_with_retry` used by the REST API. Contention between two trains wanting the same block is resolved by route-hop distance (farther train holds; ties break lexically by train_id — see `resolve_contention`'s docstring for the full rationale).
- `dispatcher/dispatcher.py::Dispatcher` is the orchestrator: on each tag event it updates position, releases the chain of blocks just cleared, and either advances the train (stop/resume via the *same* `TrainController.handle_command` used by the REST API) or holds it. A watchdog stops every train if one misses an expected tag within `dispatcher_watchdog_timeout`, auto-clearing once that train's tag reappears.
- **Actuation is in-process, not via MQTT** — the dispatcher calls `TrainController`/`SwitchController` directly (it's constructed via `dispatcher/factory.py::build_dispatcher` sharing `controller.train_controller`/`controller.switch_controller` from `webservice/train_service.py`'s `LegoController` singleton). `MqttBridge.publish_command()` exists for future direct Pico-side motor control but isn't called yet, since the Pico firmware currently only logs command messages.
- Manual REST commands (`/train`) **bypass the dispatcher entirely** in this version — no reconciliation between manual control and dispatcher-driven movement. `Train.hub_id` (and everywhere `TrainController.handle_command` is called) is a BLE address string, not an integer -- trains are controlled over GATT, unlike switches.
- Wired into `webservice/train_service.py`'s existing `startup_event`/`shutdown_event` via `asyncio.create_task(dispatcher.run())` / `await dispatcher.stop()`, gated by `settings.dispatcher_enabled` (tests force this off via `DISPATCHER_ENABLED=false` in `tests/conftest.py`, since there's no broker in CI).
